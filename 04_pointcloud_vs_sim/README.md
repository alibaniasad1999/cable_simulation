# Part 4 — Real cable point cloud (.ply) vs simulation

> Study notes. Prerequisites: Part 2 (cable with chosen size/segments/stiffness)
> and Part 3 (cable held by the gripper, Option K).
>
> **The question of this part:** you have a `.ply` point cloud of a real cable
> held in a real Franka hand. Rebuild the same situation in simulation and
> answer *"how different are they, in millimetres, and is that difference
> real or measurement noise?"*

## What you'll be able to do at the end

- Read and understand a PLY file: its header, units, coordinate frame.
- Process a point cloud: crop, remove planes and outliers, cluster, extract a centreline.
- Find rigid transforms between frames (Kabsch / Umeyama, ICP) and know when using them is honest.
- Define and compute distances between a cloud and a simulated curve.
- Build an error budget and identify the cable's bending stiffness without fooling yourself.

## Concepts

### 1. What a point cloud is

A point cloud is just a list of 3-D points `pᵢ = (x, y, z)`, sometimes with a
colour `(r, g, b)` and/or a normal `nᵢ` per point. It has **no connectivity**
(unlike a mesh) and **no notion of "cable"**. Every bit of meaning has to be
added by you.

Properties of a real cloud you must always keep in mind:
- **noise**: each point is off by about a millimetre or more;
- **occlusion**: you only see the surfaces facing the sensor. The gripper
  fingers hide part of the cable, and the back of the cable is never seen;
- **non-uniform density**: closer surfaces get more points;
- **outliers**: "flying pixels" at depth edges, reflections.

### 2. The PLY file format

PLY ("Polygon File Format", Stanford) = a text **header** + the data. Open the
beginning of your file to read the header:

```bash
head -c 800 my_cable.ply        # header is text even if the data is binary
```

A typical header:

```
ply
format binary_little_endian 1.0      ← or "ascii 1.0" (human-readable numbers)
comment generated by ...             ← often tells you the software/sensor!
element vertex 182345                ← number of points
property float x
property float y
property float z
property uchar red                   ← optional colour (0–255)
property uchar green
property uchar blue
property float nx                    ← optional normals
property float ny
property float nz
element face 0                       ← if > 0 it's a MESH, not just a cloud
end_header
<data>
```

What to learn from it:
- `ascii` vs `binary`: binary is smaller/faster. Libraries read both.
- `element vertex N`: how many points.
- which **properties** exist (colour? normals? confidence?);
- `element face`: if present with N > 0, you have a **mesh** (e.g. from a
  scanning app). You can use its vertices as a cloud, or sample its surface.
- `comment` lines: often the sensor or app name, which tells you the units/frame
  conventions (next section).

Tools: **Open3D** (`read_point_cloud`) and `plyfile` in Python; **CloudCompare**
and **MeshLab** (free GUIs) for looking at it, measuring distances by clicking,
and picking points. Spend 30 minutes in CloudCompare with your file before
writing any code.

### 3. Two questions the PLY does NOT answer by itself: units and frame

**Units.** PLY has no unit field. Check the bounding-box size: a 0.5 m cable →
extents ≈ 0.5 means metres; ≈ 500 means millimetres. **Photogrammetry** clouds
(reconstructed from many photos, e.g. Metashape, COLMAP, some phone apps) can
have an **arbitrary scale** unless they were scaled with a reference. Phone LiDAR
and depth cameras are metric.

**Frame.** The coordinates are relative to *something*:

| source | typical frame |
|---|---|
| depth camera (RealSense, ZED, Azure Kinect), single view | the **camera optical frame**: x right, y **down**, z forward (into the scene) |
| scanning app / photogrammetry | an arbitrary frame chosen by the software; often **Y-up** |
| already processed by someone | maybe the robot base frame. Ask! |

Write down what you find in a **data card** for each capture (a small YAML next
to the PLY): source/sensor, units, frame, number of points, what's visible
(cable / gripper / table / arm), the cable's free length (tape measure), and the
robot joint angles if recorded.

### 4. What you need to rebuild the scene: physics tells you

The real cable is at rest. Its shape relative to the hand is determined by:

1. **the grasp**: where along the cable and at what angle the fingers hold it
   (`T_hand_grasp`);
2. **the direction of gravity relative to the hand**;
3. **the cable**: free length, weight per metre `w`, bending stiffness `EI`
   (and any natural curl);
4. anything it touches (the arm, the table).

So to compare, you need the **hand pose in the cloud frame** (`T_cloud_hand`) and
the **gravity direction in the cloud frame** (`ĝ_cloud`). You do **not**
necessarily need the joint angles. In the simulation, put the hand anywhere as
long as its orientation relative to gravity matches. (Include the arm if the
cable touches it.)

### 5. Getting `T_cloud_hand`: three routes

**Route A — Calibration + joint angles.** If the camera was hand-eye calibrated
(`T_base_camera` known) and you recorded `q`, then
`T_camera_hand = T_base_camera⁻¹ · FK(q)`. Gravity is `−z` of the base frame.
Cleanest, but needs the calibration done at capture time.

**Route B — Register the gripper.** The gripper is visible in the cloud, and you
have its exact 3-D mesh (the Franka hand's visual mesh from the URDF package). Fit
the mesh to the gripper points:
1. *rough alignment*: click 3–4 corresponding points (fingertips, hand corners)
   on the mesh and in the cloud, then solve with **Kabsch** (below);
2. *refinement*: **ICP** of the mesh onto the gripper points only.

This is honest because you align using the **gripper**, never the **cable**.

**Route C — Manual only.** Click points as in B1 and skip ICP. Less accurate,
but quick for a first comparison.

**Gravity** for routes B/C: the **table plane normal** (RANSAC plane fit, §6),
if the table is level; or the camera's built-in **IMU** (e.g. RealSense D435i/D455)
if it was recorded; or a visible robot base.

#### Kabsch algorithm (rigid fit from point pairs)

Given matched points `aᵢ` (mesh) and `bᵢ` (cloud), find `R, t` minimising
`Σ ‖R aᵢ + t − bᵢ‖²`:

```
1. centroids ā, b̄;  centred a'ᵢ = aᵢ − ā,  b'ᵢ = bᵢ − b̄
2. H = Σ a'ᵢ b'ᵢᵀ                (3×3)
3. SVD:  H = U Σ Vᵀ
4. R = V · diag(1, 1, det(V Uᵀ)) · Uᵀ     ← the det fixes reflections
5. t = b̄ − R ā
```

**Umeyama** is the same plus a **scale** factor. Use it if your cloud's scale
is unknown (photogrammetry). The gripper's known size then fixes the scale!

#### ICP (Iterative Closest Point)

Repeat: for each source point find the nearest target point → Kabsch on these
pairs → apply. It converges only from a **good initial guess** (hence the clicks),
and it will happily lock onto the wrong surface if you leave cable points in the
target. Crop to the gripper first.

### 6. Cleaning and segmenting the cloud

Build a pipeline where **every step saves its output** so you can look at it:

1. **Crop** to a box around the gripper and cable (axis-aligned, or in the hand frame).
2. **Voxel downsampling**: one point per small cube (e.g. 1–2 mm). Evens out
   density and speeds everything up.
3. **Plane removal with RANSAC**: repeatedly pick 3 random points, fit a plane,
   count points within a threshold. Keep the plane with most inliers. Removes
   the table, and gives you its normal (gravity!).
4. **Statistical outlier removal**: for each point, the mean distance to its `k`
   nearest neighbours. Drop points whose value exceeds `mean + n·std` over the cloud.
5. **Remove the gripper**: delete points within a few mm of the registered gripper
   mesh (route B) or crop in the hand frame.
6. **Clustering with DBSCAN**: points closer than `eps` are connected, and
   clusters need at least `min_points`. Keep the cluster touching the gripper. A
   cable is long and thin, so choose `eps` a few times the point spacing.
7. **Optional colour filter** if the cable has a distinct colour.

Fast neighbour searches everywhere use a **KD-tree** (`scipy.spatial.cKDTree`,
Open3D's `KDTreeFlann`). Learn it once and use it for everything here.

### 7. From cable points to a centreline

The points lie on the **surface** of a tube of radius `r`, and only on the side
facing the camera. Useful fact: the centroid of a uniformly sampled half-circle
of radius `r` is `2r/π ≈ 0.64 r` from the axis. So naive averaging puts the
centreline too close to the camera.

Methods, simplest first:

- **Slicing**: if the cable is roughly monotonic along some direction, cut it
  into thin slices along that direction and take each slice's centroid. Simple,
  but fails if the cable loops back.
- **Graph method (general)**: k-nearest-neighbour graph → **minimum spanning
  tree** → the **longest path** in the tree (graph diameter), starting from the
  point nearest the gripper. This orders the points along the cable.
- **Smoothing**: fit a smoothing spline (`scipy.interpolate.splprep`), then
  **resample at equal arc-length steps** (e.g. every 2 mm).
- **Correct the surface bias**: shift by ~`2r/π` away from the camera, or (better,
  advanced) fit a tube: adjust the centreline so that points sit at distance `r`.

**Length check (critical):** extracted length + hidden length in the fingers ≈
tape-measured free length. Noise makes a zig-zag that **inflates** length.
Occlusion **shortens** it. If the check fails by more than a few %, fix the
segmentation before comparing anything.

### 8. Rebuilding the scene in Newton

Use **Option K** from Part 3 (kinematic attachment). It gives you exact control
of the grasp, which is the thing you must match. Every number comes from the data card:

| Newton input | where it comes from |
|---|---|
| `Rod.create_straight(length=...)` | tape-measured **free length** (fingers → tip). If held in the middle, two lengths and `grasp_body = N//2`. |
| `radius` | calipers |
| `density` | weighed mass per metre / (π r²), Part 2 §2.5 |
| `segment_count` | from your convergence test (Part 2 §2.4) |
| `bend_stiffness` | start from the table-edge `EI` (Part 2 §2.6), then **identified** in §11 |
| `stretch_stiffness`, iterations | high enough that stretch < 0.5 % (Part 2 §2.6, §2.7) |
| hand pose | **Route A**: recorded joint angles → `joint_q` → `eval_fk`. **Routes B/C**: any robot pose whose hand orientation relative to gravity equals the measured one (IK with that rotation target), or skip the robot and move only the clamped cable body. |
| `T_tcp_grasp` | from the photo / the cloud near the fingers: where the cable leaves the fingers and at what angle |
| floor/table | only if the real cable touches it; at the measured height |

Then:
1. start the cable straight along the grasp direction;
2. step until **settled** (tip moves < 0.1 mm per 0.1 s for 1 s);
3. read the cable bodies → nodes (Part 2 §2.9);
4. transform the nodes into the cloud frame: `T_cloud_tcp · T_tcp_world · nodes`;
5. save them (`.npy`) next to the capture. The comparison code (§9) reads files
   and never needs Newton. Keep the two parts separate.

**Parameter sweeps with worlds:** put each candidate `bend_stiffness` in its own
world (Part 3 §3.5). One run then gives you the whole sweep for §11.

> **Never ICP-align the simulated cable to the real cable.** Both live in the same
> frame through the gripper. Aligning the cables would absorb exactly the error you
> are trying to measure.

### 9. Measuring the difference

Distance from a point `p` to a segment `[a, b]`:

```
t = clamp( (p − a)·(b − a) / ‖b − a‖², 0, 1 )
d = ‖ p − (a + t (b − a)) ‖
```

Distance from a point to a polyline = minimum over its segments.

| metric | definition | why |
|---|---|---|
| **cloud→sim surface error** | for each real cable point: `d(p, sim centreline) − r`. Report mean, RMS, 95th percentile, max. | **Main metric.** Uses only what you saw, so it's robust to occlusion. |
| **coverage** | fraction of the sim centreline within e.g. 5 mm of some real point | catches sim cable where there is no real cable (wrong length or wrong place) |
| **arc-length error `e(s)`** | `‖c_real(s) − c_sim(s)‖` at equal arc length `s` from the grasp | *where* the error is: growing from the grasp means a wrong angle/stiffness; only near the tip means wrong length |
| **tip error** | distance between the free ends | one intuitive headline number |
| **Chamfer distance** | `mean_p min_q ‖p−q‖ + mean_q min_p ‖q−p‖` | standard in papers, but symmetric, so it's hurt by occlusion |
| **Hausdorff distance** | the worst-case of the above | sensitive to outliers. Report, don't optimise. |

### 10. Error budget: is the difference real?

Every input has an uncertainty. Estimate each:

| source | how to estimate | typical size |
|---|---|---|
| sensor noise | spread of points on the flat table around the RANSAC plane | 0.5–3 mm |
| gripper registration | ICP residual; repeat with different initial clicks | 1–5 mm, 1–2° |
| gravity direction | table-normal fit vs IMU, if both available | 0.5–2° |
| grasp angle/offset | from the photo; repeat the estimate | a few degrees. A 5° error moves a 0.5 m cable's tip by ~4 cm, so **usually the biggest term** |
| free length | repeat the tape measurement | 1–3 mm |
| `w`, `EI` | repeated weighing; table-edge test at several overhangs | 5–30 % on `EI` |

**Propagate by simulation (Monte Carlo):** run the sim ~20–50 times with each
input randomly perturbed within its uncertainty. The spread of the metrics is the
**noise floor**. If sim-vs-real error ≈ noise floor, the honest conclusion is
*"the simulation agrees with reality within measurement accuracy"*. That's a
good result, not a failure.

### 11. Identifying `EI`, and not fooling yourself

1. **Sweep** `EI` on a log scale (e.g. 10⁻⁶ … 10⁻² N·m²) and plot the main metric
   vs `EI`. Look at the curve's shape: a sharp minimum means `EI` is well
   identified; a flat valley means this capture can't tell you `EI`.
2. Refine with a 1-D search (golden-section) around the minimum.
3. **Identifiability**: a cable held pointing straight **down** hangs straight
   whatever `EI` is, so the curve is flat. A cable leaving the hand
   **horizontally** droops by an amount that depends strongly on `EI`, so the
   minimum is sharp. Part 2, Task 6 (bend stiffness sweep) shows this effect directly.
4. **Ambiguity**: a lower tip can mean a *softer* cable **or** a grasp *tilted
   down*. If you fit both `EI` and the grasp angle, they trade off. Plot the 2-D
   error map and look for a long valley. Several captures at different hand
   orientations break the ambiguity.
5. **Fit on one capture, validate on others.** Error on the captures you didn't
   fit on is the number that means something. Report both.

### 12. Test the whole pipeline on synthetic data first

You can't check the real pipeline against a known answer, but you **can** make
a fake PLY with a known answer:

1. simulate a cable with a known `EI` and grasp;
2. sample points on its tube surface;
3. keep only points facing a virtual camera (normal · view direction < 0);
4. add Gaussian noise (σ ≈ 1 mm), some outliers, and remove the part "hidden by fingers";
5. write it as a PLY with a plausible header and frame;
6. run your full pipeline and check you recover the `EI` and get a near-zero error.

If your pipeline can't recover a known answer from perfect-ish fake data, it
certainly won't from real data. This is the 3-D equivalent of the legacy
project's "check the ODE against the closed-form catenary" step.

## Exercises

1. **PLY by hand.** Write a 10-point ASCII PLY file in a text editor and load it.
   Then convert your real file to ASCII and look at a few lines.
2. **Kabsch from scratch.** Implement it with numpy SVD. Test: rotate+translate a
   random point set, add noise, recover the transform. Then make a reflection test
   case and see what the `det` term does.
3. **ICP basin of attraction.** Start ICP on the gripper from initial guesses rotated
   by 5°, 15°, 30°, 60°. When does it fail?
4. **RANSAC parameters.** How many iterations does RANSAC need to find the table
   with 99 % probability if 30 % of points are table? (Hint:
   `N = log(1−0.99) / log(1−0.3³)`.) Check against what you observe.
5. **Surface bias.** Using the synthetic generator, measure the offset between the
   naive centroid centreline and the true one. Compare with `2r/π`.
6. **Length bias.** Add noise σ = 0.5, 1, 2 mm to a synthetic cable and measure the
   extracted length with and without smoothing.
7. **Metric behaviour.** On synthetic data, compare cloud→sim, Chamfer and Hausdorff
   as you increase occlusion. Which one is fair to use as the main metric, and why?
8. **Identifiability map.** With synthetic data, plot the error vs `EI` for grasp
   angles of 0° (horizontal), 45° and 90° (down). Which capture would you
   choose to take in the lab?

## Common mistakes

- Assuming the PLY is in metres and/or in the robot frame without checking.
- Camera optical frame (y down, z forward) mistaken for a Z-up world frame.
- ICP with cable points still in the target, so the gripper "slides" along the cable.
- Comparing to the raw surface points without subtracting the radius.
- Aligning the sim cable to the real one (hides the error).
- Fitting `EI` on a capture where the cable hangs straight down (not identifiable).
- Fitting and reporting the error on the same single capture.
- Forgetting the cable length hidden between the fingers.
